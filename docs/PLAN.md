# pdlscore — Padel Americano: MVP

Цель: как можно быстрее получить работающий MVP. Один стек, один сервис, деплой по push.

## Скоуп MVP

**Входит:**
- 4, 8, 12 или 16 игроков (по умолчанию 4), N/4 кортов, N−1 раундов. Каждый по разу играет в паре с каждым и ровно дважды против каждого (циклический whist-дизайн, см. `schedule.ts`). Для 4 игроков — 1 корт, 3 игры:
  | Игра | Пара 1 | Пара 2 |
  |---|---|---|
  | 1 | P1 + P2 | P3 + P4 |
  | 2 | P1 + P3 | P2 + P4 |
  | 3 | P1 + P4 | P2 + P3 |
- Настройка: число игроков, имена и очки за игру (по умолчанию **32**; варианты 16, 21, 24, 32).
- Ввод результата: сетка кнопок **0…N**. Нажатие на число у пары 1 ставит паре 2 значение `N − x` автоматически, и наоборот. Результат можно исправить.
- Таблица на текущий момент: место, игрок, сумма очков, сыгранные игры, победы, разница (набрано − пропущено). Сортировка: очки ↓, затем победы ↓, затем разница ↓.
- Таблица пересчитывается после каждого введённого результата.

**Не входит (позже):** авторизация, список и история турниров, число игроков не кратное 4 (с отдыхающими), Mexicano, live-обновление без перезагрузки, C#-бэкенд, переход на PostgreSQL (см. «Следующий этап»).

## Стек

- **SvelteKit (Svelte 5) + TypeScript, SSR**, `@sveltejs/adapter-node`. Один Node-процесс отдаёт и страницы, и данные.
- Изменения идут через **form actions** (`<form method="POST">` с `use:enhance`). Ввод счёта работает даже без JS, а с JS страница не перезагружается.
- **SQLite** через `better-sqlite3`, файл `data/app.db`. Без ORM, 2 таблицы и простой SQL. Миграция — `CREATE TABLE IF NOT EXISTS` при старте.
- Тесты: **Vitest** для доменной логики (расписание, таблица).
- Стили: обычный CSS в компонентах, mobile-first (телефон у корта). Без UI-библиотек.

## Модель данных

```sql
CREATE TABLE IF NOT EXISTS tournament (
  id TEXT PRIMARY KEY,          -- короткий случайный id для ссылки
  players TEXT NOT NULL,        -- JSON-массив имён (4/8/12/16), число игроков = длина массива
  points_per_game INTEGER NOT NULL DEFAULT 32,
  created_at TEXT NOT NULL DEFAULT (datetime('now'))
);
CREATE TABLE IF NOT EXISTS game (
  tournament_id TEXT NOT NULL REFERENCES tournament(id),
  idx INTEGER NOT NULL,         -- 0..N(N-1)/4-1, номер игры в расписании generateSchedule(N)
  score1 INTEGER,               -- NULL = не сыграна
  score2 INTEGER,
  PRIMARY KEY (tournament_id, idx)
);
```

## Страницы

- `/` — форма: число игроков (без JS — ссылки `?players=8`), имена и очки за игру, кнопка «Начать». Создаёт турнир и делает редирект на `/t/[id]`.
- `/t/[id]` — карточки игр (при 8+ игроках сгруппированы по раундам, с номером корта) (пары, счёт, кнопка «Ввести/изменить») и таблица ниже. Ссылку можно отправить игрокам: все видят одно и то же (обновление по перезагрузке).
- `/t/[id]/game/[idx]` — ввод счёта: две колонки кнопок 0…N, выбранное значение подсвечено, вторая колонка заполняется автоматически, кнопка «Сохранить».

## Структура кода

```
src/lib/domain/schedule.ts      // расписание для 4/8/12/16 игроков

src/lib/domain/*.test.ts

```

Доменная логика — чистые функции без зависимостей от SvelteKit и БД. Позже её можно перенести в C# один к одному.

## Деплой (минимально)

- `Dockerfile`: multi-stage на node:22-alpine, `npm ci && npm run build`, запуск `node build`, порт 3000. Том для `/app/data`.
- На VPS приложение работает в Docker за общим обратным прокси, который проксирует домен на `:3000` и сам выпускает HTTPS.
- **GitHub Actions**:
  1. `ci.yml` на `pull_request` и `push`: `npm ci`, `npm run check`, `npm test`, `npm run build`. Без секретов.
  2. Деплой — отдельный workflow только на `push` в `main` (никогда на `pull_request` или `pull_request_target`), после зелёных проверок.
- Домен: `pdlscore.fun` и `www.pdlscore.fun`, www редиректит на корень.
- Настройка сервера и прокси живёт вне этого репозитория.

## Публичный репозиторий

Репозиторий **публичный**. Поэтому:
- В репозиторий не попадают IP VPS, имя пользователя, ключи, `.env` и `data/`. Всё это хранится только в GitHub Secrets или в `.env` на сервере.
- Секреты используются только в workflow деплоя на push в `main`. PR из форков секретов не получают и деплой не запускают.
- В репозитории есть `README.md` и `LICENSE` (MIT).

## Следующий этап: PostgreSQL вместо SQLite

Зачем: смотреть и разбирать данные турниров обычными инструментами (psql, DBeaver, pgAdmin), не заходя в контейнер к файлу `data/app.db`.

- Postgres — отдельный контейнер в compose на сервере, с томом для данных. Наружу порт не открывается, доступ для просмотра — через SSH-туннель.
- Строка подключения — `DATABASE_URL` в `.env` на сервере, в репозиторий не попадает.
- Драйвер `postgres` (porsager) или `pg`, по-прежнему без ORM. Схема та же: `players` как `jsonb`, `created_at` как `timestamptz`.
- Слой `src/lib/server` становится асинхронным, доменная логика не меняется.
- Миграция данных: одноразовый скрипт переносит `tournament` и `game` из SQLite в Postgres.
- Локально Postgres запускается через `docker compose`, для CI в workflow добавляется service-контейнер, если появятся тесты на БД.
- Отдельный пользователь Postgres только на чтение, для просмотра данных.

## Критерии готовности MVP

- [ ] `npm run check`, `npm test`, `npm run build` зелёные.
- [ ] Тесты: расписание даёт 3 игры, каждый игрок в паре с каждым ровно раз; таблица верно считает очки, победы, разницу и сортировку, в том числе при частично введённых играх и ничьей (16:16).
- [ ] С телефона можно создать турнир, ввести 3 результата и увидеть итоговую таблицу.
- [ ] Push в main → через 1–2 минуты новая версия на VPS.
